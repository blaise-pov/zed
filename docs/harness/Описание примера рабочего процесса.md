### ЭТАП 1. Получение задания и фаза согласования (Approval Gate)

Оркестратор начинает любую работу в фазе обсуждения:
1. **Feasibility Gate**: оценивает архитектурную целесообразность изменений и затраты на реализацию. Если задача противоречит архитектуре или неоправданно дорога, оркестратор останавливается и предлагает альтернативы текстом в чате.
2. **План в чате**: формулирует архитектурный план и декомпозицию задач **строго текстом в чате**. В этой фазе запрещены любые файловые мутации, создание задач в графе и запуск субагентов.
3. **Approval Gate**: ожидает явного и однозначного подтверждения пользователя («делай», «ок», «go ahead») перед переходом к любым действиям.
4. **Clean Base Gate**: проверяет чистоту рабочей копии на ветке `main` через `git --no-optional-locks status`. При наличии незафиксированных изменений выполнение останавливается с требованием закоммитить или спрятать изменения в stash.

### ЭТАП 2. Создание Goal и Tasks в TaskGraph Service (TGS)

После одобрения пользователя оркестратор регистрирует сущности в TGS через MCP-инструменты:

1. **Создание Goal** через `goal_create`:
   ```json
   {
     "title": "Интеграция пула субагентов",
     "description": "Ограничение параллелизма и очереди ворктри",
     "priority": 1
   }
   ```
   *Автоматическое связывание*: Если поле `session_id` не передано, рантайм автоматически подставляет идентификатор текущей сессии чата. Это связывает графический интерфейс панели задач с контекстом диалога.

2. **Создание графа Tasks** через `task_create` (пакетом в единой транзакции):
   ```json
   {
     "tasks": [
       {
         "temp_id": "core-engine",
         "goal_id": "GOAL-10",
         "title": "Реализация ядра пула слотов",
         "write_scopes": ["crates/agent/src/**"],
         "acceptance_criteria": ["Пул слотов корректно обрабатывает конкурентные запросы"],
         "depends_on": []
       },
       {
         "temp_id": "ui-indicator",
         "goal_id": "GOAL-10",
         "title": "Индикатор активных слотов в Task Panel",
         "write_scopes": ["crates/agent_ui/src/**"],
         "acceptance_criteria": ["Отображение состояния пула в UI панели задач"],
         "depends_on": ["core-engine"]
       }
     ]
   }
   ```
   *Динамические Task Write Scopes*: Поле `write_scopes` в задаче задает контрактный файловый периметр конкретного таска. Оркестратор распределяет параллельные задачи по взаимоисключающим путям, исключая конфликты при одновременной работе.
   *Управление зависимостями*: Задачи без зависимостей сразу получают статус `Ready`. Задачи с зависимостями (`ui-indicator`) регистрируются в статусе `Blocked` и остаются заблокированными до завершения предшествующих задач.

**Настройка интеграции**:
- `agent.task_graph_server_id` (`string`, по умолчанию в коде: `"tgs"`, в настройках проекта: `"taskgraph"`): ключ MCP-сервера графа задач в блоке `context_servers`.

### ЭТАП 3. Запуск задач через `spawn_agent` и контроль ограничений

Оркестратор параллельно вызывает `spawn_agent` для независимых задач в статусе `Ready`:
```json
{
  "label": "Implement pool core",
  "profile": "agent_engineer",
  "task_id": "TASK-1",
  "goal_id": "GOAL-10",
  "message": "Реализовать SubagentSlotPool в crates/agent/src/thread.rs. Fast gate: cargo check -p agent --lib."
}
```

Перед инициализацией рантайм выполняет каскад проверок:

#### 1. Валидация существования и статуса задачи в TGS
- Задача обязана существовать в TGS.
- **Контроль статуса задачи**:
  - При создании нового субагента (`session_id` не передан) статус задачи **обязан быть строго `Ready`**. Если задача находится в статусе `Blocked`, `Running`, `Completed` или любом другом, вызов немедленно отклоняется с ошибкой:
    ```text
    Cannot spawn agent for task '<task_id>': status is '<status>', expected 'ready'. Resolve dependencies first or update status via task_update.
    ```
  - При возобновлении сессии (`session_id` передан) разрешены только статусы `Ready`, `Running`, `Completed`, `Failed`, `Review`. Статусы `Blocked`, `Cancelled`, `Archived`, `Stale` блокируют запуск.
  - В гостевом режиме целевая задача также обязана находиться в статусе `Ready`.
  - При ручном режиме управления жизненным циклом (`task_lifecycle_mode: "agent"`) валидация статуса отключается.

#### 2. Лимиты сессий и параллелизма
- **Защита от параллельных сессий одной задачи**: Защитный страж блокирует запуск, если задача или целевой хост-ворктри уже имеют активную сессию.
- **Семафор сессий субагентов (`SubagentSlotPool`)**:
  - Атомарный счетчик активных субагентов на уровне всего дерева сессии.
  - Лимиты: `agent.nested_sub_agents.max_concurrent` (по умолчанию `16`, допустимо `1..=32`) и `agent.nested_sub_agents.max_depth` (по умолчанию `1`, допустимо `1..=5`). При превышении вызов отклоняется с ошибкой `"Concurrent sub-agent limit reached"`.
- **Лимитер сетевых запросов к LLM (`ModelRateLimiters`)**:
  - Ограничивает параллельные вызовы к конкретной модели (лимит по умолчанию: `16`).
  - Перед запуском любых инструментов тред принудительно сбрасывает поток модели (`drop(events)`), возвращая слот в пул во избежание deadlock'ов при рекурсивном вызове субагентов.

#### 3. Лимит параллельных Worktree на диске
- **Ограничение**: `agent.task_worktree_limit` (по умолчанию в коде: `3`, в настройках проекта: `6`, минимум `1`).
- **LRU-вытеснение**: При исчерпании лимита рантайм находит безопасные неактивные ворктри, сортирует их по времени завершения последней сессии и удаляет старейший.
- **Очередь ожидания слота**: Если все ворктри заняты, запрос встает в FIFO-очередь ожидания с таймаутом **45 секунд**.

#### 4. Изоляция и подготовка окружения
- Ленивое ветвление: ветка цели `agent-goal/{goal_id}` создается от актуального HEAD репозитория в момент первого обращения.
- Каталог `agent-task-{task_id}` и ветка `agent-task/{task_id}` создаются ответвлением от текущего состояния `agent-goal/{goal_id}`.
- Профиль `agent_engineer` имеет настройку `task_isolation: "required"`, что гарантирует создание изолированного ворктри.
- `agent.task_worktree_language_servers` (по умолчанию: `true`, в настройках проекта: `false`): отключает старт серверов LSP в каталогах временных ворктри.
- **Инъекция контракта задачи**: На первом ходе рантайм извлекает метаданные таска из TGS и вставляет в начало промпта субагента блок `<task_contract>` (название, цель, критерии приемки, ограничения и `Write Scopes` таска).
- **Регистрация метаданных**: Рантайм регистрирует используемую модель, профиль и сессию в TGS и переводит задачу в статус `Running`.

### ЭТАП 4. Выполнение работы субагентом-инженером

Субагент работает внутри изолированного каталога:

- **Двухуровневые Write Scopes (Контракт таска vs Барьер профиля)**:
  - *Контрактный уровень (Task Scopes)*: модель ориентируется на пути, переданные в блоке `<task_contract>`, фокусируясь только на порученной подзадаче.
  - *Аппаратный уровень (Profile Scopes)*: настройки профиля в `.zed/settings.json` задают жесткий абсолютный барьер безопасности роли (`Task.write_scopes ⊆ Profile.write_scopes`). Если субагент попытается изменить файлы вне разрешенных путей профиля или выйти за границы каталога через симлинки, операция немедленно блокируется рантаймом с ошибкой `PolicyDenied`.
- **Fail-Closed**: В автономном режиме любые интерактивные диалоги подтверждения действий автоматически отклоняются с ошибкой `PolicyDenied`.
- **Сторожевые таймеры**: Таймаут отправки промпта (`send_watchdog_seconds: 30s`) и таймаут ответа модели (`turn_watchdog_seconds: 120s`).
- **Быстрые проверки**: Разрешены только быстрые валидации (`cargo check -p <crate> --lib`) и целевые модульные тесты. Запуск полных тестовых наборов и тяжелых линтеров запрещен.
- **Финальный отчет**: Завершение оформляется строго финальным YAML-блоком:
  ```yaml
  status:   done
  summary:  Реализован SubagentSlotPool в thread.rs
  blockers: none
  detail:   branch agent-task/TASK-1
  ```

### ЭТАП 5. Автоматический пост-процессинг рантайма и разблокировка зависимостей

В режиме `task_lifecycle_mode: "runtime"` рантайм автоматически выполняет цепочку шагов:

1. **Commit-on-completion**:
   - Изменения автоматически фиксируются в ветку задачи `agent-task/{task_id}`.
   - *Фильтрация по Task Scopes*: рантайм сверяет измененные файлы со скоупом задачи, исключая случайную фиксацию служебных файлов (например, внедренного файла `.zed/settings.json`).
   - При успешном завершении сообщение коммита формируется из заголовка задачи в TGS. При сбое сессии создается коммит вида `WIP: <branch> error checkpoint`.
2. **Merge-back в ветку цели (`agent-task/{task_id} -> agent-goal/{goal_id}`)**:
   - Выполняется слияние на уровне git plumbing без переключения рабочего дерева:
     - *Fast-Forward*: Атомарный сдвиг указателя ветки цели при отсутствии параллельных коммитов.
     - *Clean 3-way merge*: Создание merge-коммита в ветку цели без переключения рабочего каталога.
     - *Merge Conflict*: Фиксация конфликта слияния. Ворктри задачи сохраняется на диске для разбора, а автоматическое удаление каталога отменяется.
3. **Публикация реф-артефакта (`publish_ref_artifact`)**:
   - Рантайм публикует в TGS артефакт `task_ref` со ссылкой на ветку, SHA коммита, статус слияния и список конфликтов (при наличии).
4. **Снятие диффа и телеметрия (`task_record_turn`)**:
   - Вычисляется статистика измененных строк и файлов относительно базового состояния.
   - В TGS отправляется отчет телеметрии: использованные токены, длительность, модель, commit SHA, краткая сводка диффа и вывод агента.
5. **Перевод задачи в статус `Completed`**:
   - Рантайм выставляет задаче статус `Completed` в TGS.
   - TGS автоматически снимает блокировку с зависимых задач в графе (`Blocked` -> `Ready`).
   - Разблокированные задачи при последующем запуске ответвятся от обновленного состояния `agent-goal/{goal_id}`, уже содержащего наработки родительской задачи.
6. **Очистка каталога Worktree и Retention**:
   - Если параметр `cleanup` включен (`true`), рантайм удаляет каталог ворктри с диска.
   - **Удержание зависимостями**: Если от текущей задачи зависят другие задачи в статусе `Ready` или `Running`, удаление каталога откладывается. Это сохраняет файлы и прогретый кеш компилятора для гостевого ревьюера (`reviewer` с параметром `worktree_of`).
   - Окно удержания `task_worktree_retention_timeout_seconds` задает дополнительное время сохранения каталога на диске.
   - Ветка `agent-task/{task_id}` в Git всегда сохраняется.
   - После удаления ворктри рантайм отправляет сигнал в очередь ожидания, освобождая слот для следующей задачи.

### ЭТАП 6. Двухэтапный контроль ветки цели (Reviewer + CI Verifier)

Для целей из трех и более задач оркестратор закрывает цель обязательным двухэтапным гейтом:

1. **Код-ревью (`reviewer`)**:
   Оркестратор запускает `reviewer`, монтируя ветку цели через `on_branch: "agent-goal/{goal_id}"` с передачей `task_id`:
   - Ревьюер работает строго в режиме чтения, без запуска тестов и сборки.
   - Проверяет дифф ветки цели против ТЗ и правил репозитория.
   - Возвращает отчет с обязательными строками вердикта:
     ```yaml
     status:   done
     summary:  Goal diff matches acceptance criteria
     blockers: none
     detail:   none
     verdict:  approve
     findings: []
     ```
2. **Удаленная верификация на GitHub Actions (`ci_verifier`)**:
   После одобрения ревьюером оркестратор запускает `ci_verifier` (профиль с отключенной изоляцией ворктри, работающий в общем каталоге):
   - Отправляет ветку цели на удаленный сервер: `git push origin agent-goal/{goal_id}`.
   - Запускает рабочий процесс верификации: `gh workflow run agent_verify.yml --ref ...`.
   - Ожидает завершения проверки: `gh run watch <run-id> --exit-status`.
   - Пайплайн выполняет полный прогон Clippy и тестов на стенде Windows runner.
   - Команды верификатора ограничены белым списком терминала: по умолчанию `deny`, автопуск только для сетевых команд `git` (`push`, `fetch` и др.) и `gh` (см. профиль `ci_verifier` в `.zed/settings.json`). Сетевой доступ песочницы согласовывается отдельным запросом.
   - Возвращает отчет:
     ```yaml
     status:   done
     summary:  CI workflow passed on GitHub Actions
     blockers: none
     detail:   https://github.com/zed-industries/zed/actions/runs/778899
     verdict:  green
     findings: none
     ```

### ЭТАП 7. Интеграция в main и Graduation Cleanup

1. **Squash merge в ветку main (`git_merger`)**:
   Оркестратор передает задачу слияния специализированному агенту `git_merger`:
   - Переключается на основную ветку: `git switch main`.
   - Проверяет чистоту: `git --no-optional-locks status --porcelain` (обязан быть пуст).
   - Выполняет слияние: `git merge --squash agent-goal/{goal_id}`.
   - *При возникновении конфликта*: сбрасывает состояние (`git reset --hard HEAD`) и вызывает `merge_resolver`, который разрешает семантические конфликты, проверяет сборку и завершает коммит.
   - При чистом слиянии создает коммит с обязательным префиксом подсистемы `<scope>: <Imperative verb> ...`, меткой `Goal: GOAL-10` и блоком `Release Notes:`.
2. **Перевод Goal в статус Completed**:
   Оркестратор завершает цель через вызов `goal_update`:
   ```json
   {
     "goal_id": "GOAL-10",
     "status": "completed"
   }
   ```
3. **Автоматическая зачистка веток (`cleanup_graduated_goal`)**:
   - Переход цели в финальный статус перехватывается хранилищем задач в рантайме.
   - Проверяется, что все задачи цели находятся в терминальном статусе.
   - Защита базовых веток блокирует случайную модификацию или удаление веток `main`, `master` и служебных ссылок `HEAD`.
   - При `agent.delete_task_branches_on_graduation: true` удаляются все временные ветки задач `agent-task/*`.
   - При `agent.delete_goal_branches_on_graduation: true` удаляется интеграционная ветка цели `agent-goal/*`.
   - Базовая ветка определяется параметром `agent.goal_graduation_base_branch` (по умолчанию `null` с автоматическим откатом к ветке репозитория по умолчанию или `main`).
